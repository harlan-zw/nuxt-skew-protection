Nitro supports the `aws_lambda` and `aws_amplify` presets. Use polling by default on both platforms.

| Deployment | Update strategy | Previous asset storage | Request affinity |
|---|---|---|---|
| AWS Lambda | Polling | S3 or another shared store | None by default |
| Amplify Hosting | Polling | Explicit Amplify build cache | None |
| Self-managed CloudFront and Lambda | Polling or external adapter | S3 | Possible with custom origin routing |

## AWS Lambda

Configure polling explicitly:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    preset: 'aws_lambda'
  },
  skewProtection: {
    updateStrategy: 'polling'
  },
  experimental: {
    checkOutdatedBuildInterval: 5 * 60 * 1000
  }
})
```

Polling avoids holding a Lambda invocation open for every connected browser. Use an [external adapter](/docs/skew-protection/providers/external) for instant notifications.

### SSE limitations

Nitro buffers Lambda output unless you enable `awsLambda.streaming`. [Nitro documents this prerequisite](https://nitro.build/deploy/providers/aws#response-streaming):

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    preset: 'aws_lambda',
    awsLambda: {
      streaming: true
    }
  },
  skewProtection: {
    updateStrategy: 'sse'
  }
})
```

The ingress must also support `InvokeWithResponseStream`. Lambda currently supports response streaming through function URLs and an API Gateway proxy integration. Region support varies. Lambda billing continues for the full invocation duration, even after the browser disconnects. See [Lambda response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html).

A Lambda invocation can run for at most 900 seconds, so an SSE client must reconnect before the configured timeout. See [Lambda timeout configuration](https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html). These limits make polling the safer default.

## Amplify Hosting

Amplify deployments are atomic, but each deployment still needs access to retained Nuxt chunks. See [Amplify atomic deployments](https://docs.aws.amazon.com/amplify/latest/userguide/welcome.html#key-capabilities).

The module's default filesystem store is inside `node_modules/.cache`. Amplify omits `node_modules/.cache` when the cache includes the whole `node_modules` directory. See [Amplify cache troubleshooting](https://docs.aws.amazon.com/amplify/latest/userguide/troubleshooting-caching.html).

Move the module store outside `node_modules`, then cache it explicitly:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    preset: 'aws_amplify'
  },
  skewProtection: {
    updateStrategy: 'polling',
    storage: {
      driver: 'fs',
      base: '.amplify-cache/skew-protection'
    }
  },
  experimental: {
    checkOutdatedBuildInterval: 5 * 60 * 1000
  }
})
```

```yaml [amplify.yml]
version: 1
frontend:
  phases:
    preBuild:
      commands:
        - corepack enable
        - pnpm install --frozen-lockfile
    build:
      commands:
        - pnpm build
  artifacts:
    baseDirectory: .amplify-hosting
    files:
      - '**/*'
  cache:
    paths:
      - .amplify-cache/**/*
```

Amplify restores configured cache paths before later builds. Paths must be relative to the project root. See the [Amplify build specification](https://docs.aws.amazon.com/amplify/latest/userguide/yml-specification-syntax.html).

Keep `bundleAssets: true` unless another store or CDN retains every old chunk for at least the configured retention period.

## Lambda, S3, and CloudFront

For a self-managed deployment, put content-hashed Nuxt assets in a shared S3 namespace and retain them across releases. CloudFront recommends versioned filenames because they support concurrent versions and avoid invalidations. See [CloudFront file versioning](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/UpdatingExistingObjects.html).

Publish a release in this order:

1. Upload all new immutable assets to S3.
2. Publish and verify the new Lambda version.
3. Move the live Lambda alias or CloudFront origin mapping to the new version.
4. Publish `/_nuxt/builds/latest.json`.
5. Notify clients through the selected update strategy.

S3 provides strong read-after-write consistency and atomic updates per key. See the [S3 consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel). Publishing assets before the compute switch ensures new HTML cannot reference missing chunks. Publishing the latest manifest and notification last ensures clients cannot learn about a release before it is serving traffic.

Give `/_nuxt/builds/latest.json` a separate CloudFront behavior with caching disabled, or invalidate it after publication. A CloudFront minimum TTL above zero can override `no-cache` and `no-store` response directives. See [CloudFront cache policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-key-understand-cache-policy.html).

When S3 retains every content-hashed asset, `bundleAssets: false` can reduce the Lambda bundle. This protects chunk requests only. API and server-rendered requests still need deployment affinity when their behavior changes between releases.

## Full request affinity workaround

A weighted Lambda alias does not pin a browser to one function version. Lambda uses probabilistic routing, with a maximum of two versions behind an alias. See [Lambda weighted aliases](https://docs.aws.amazon.com/lambda/latest/dg/configuring-alias-routing.html).

A self-managed CloudFront distribution can provide deterministic affinity:

1. Retain each supported Lambda deployment as a distinct CloudFront origin.
2. Associate a JavaScript runtime 2.0 CloudFront Function with viewer requests.
3. Read the module's version cookie, `__nkpv` by default.
4. Map the cookie value through a fixed allowlist to an origin ID.
5. Call `selectRequestOriginById()`{lang="ts"} for the selected deployment.
6. Route shared content-hashed assets to S3.
7. Exclude `/_nuxt/builds/latest.json` and update notification endpoints from affinity routing.

CloudFront Functions can select another configured origin during the viewer request event. See [CloudFront origin modification](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/helper-functions-origin-modification.html#helper-functions-origin-modification-select-request-origin-by-id).

Include the version cookie in the cache key for version-sensitive HTML and data responses, or disable caching for those behaviors. Otherwise, responses from different deployment origins can share one cache entry. See [CloudFront cookie caching](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Cookies.html).

This workaround requires control of the CloudFront distribution, Lambda versions, and origin lifecycle. Retain an origin until both the module retention window and version cookie lifetime have expired.
